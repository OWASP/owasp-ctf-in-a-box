- **Fixed: the scorer and sync stop cleanly, and a slow Redis start no longer reads like the v1-data refusal (#825).** Both ran as PID 1 with no signal handler, so `docker stop` or a redeploy waited the full timeout and then killed them mid-poll or mid-score. On SIGTERM sync now ends the tick in progress at its next comment or held score (the cursor stops just before the first comment not handled, so nothing is dropped), saves its cursor and exits (at once if it is idle), retrying a cursor save that failed up to twice before it exits; only if every attempt fails does it exit on the older cursor and log `the last poll cursor was not saved`, and the next start re-reads from there, and the scorer stops accepting connections, lets a score already being judged finish its write (up to 35 seconds), answers a score that arrives after the stop began with a 503 that sync retries, and exits. So that drain is not cut off at the platform's default, `docker-compose.yml` gives the scorer a 40-second stop grace period and sync 120 seconds, the ECS task definitions set the same `stopTimeout`, and `deploy/fly/fly.toml` sets `kill_timeout = 120` (Fly's default is 5 seconds). At startup, the app, the scorer and sync used to log `Redis compatibility check failed: fetch failed` while srh was still starting, the same words as the v1-data refusal; they now log `waiting for Redis (…), retrying` and keep trying (30 tries, two seconds apart), then exit with `Redis did not answer after N tries`. A real refusal still logs `Redis compatibility check failed` once and exits. Sync's GitHub reads now time out after 15 seconds and its score submissions after 40, so a stalled request cannot hold a tick.
